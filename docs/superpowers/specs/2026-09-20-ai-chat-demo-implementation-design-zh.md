# AI 聊天 Demo：内部实现设计

**日期：** 2026-09-20

**状态：** 方案已由用户确认；尚未实现、建表或完成测试。

**用途：** 落实 [API 文档](2026-09-20-ai-chat-demo-api-design-zh.md)原第 11 节的七项设计。本文不新增前端接口，公开接口仍为 11 个；不扩展课程、Lab、Enrollment、RAG 或评分功能。

## 1. 登录、部署与限流

### 1.1 登录方案

- 前后端同站点部署：页面 `/`，接口 `/api/v1`。本地开发通过前端开发服务器代理接口，生产环境使用 HTTPS。
- 采用服务端 Session + Cookie，Cookie 名为 `chat_session`，使用 `HttpOnly`、`SameSite=Lax`、`Path=/`；生产 HTTPS 设置 `Secure`，本地 HTTP 单独配置。
- 浏览器保存不可预测的随机登录凭据；MySQL 保存其哈希、用户、到期时间和撤销状态。不能把裸凭据写入数据库或日志。
- 登录后固定 7 天有效，第一版不自动续期。退出撤销当前登录凭据并清除 Cookie，不影响其他设备。后端重启不清除有效登录。
- 密码只保存密码哈希；模型 API Key 仅放在后端配置中，不返回前端、不写入项目版本库。
- 所有浏览器写请求校验受信任的 Origin；缺少或不匹配则拒绝，JSON 请求要求正确 Content-Type。SameSite 不是唯一的跨站请求防护。
- 注册后仍按 API 约定单独登录；不增加刷新 Token、找回密码或邮箱验证接口。

### 1.2 初始限流配置

| 项目 | 上限 | 超限处理 |
|---|---|---|
| 登录请求 | 同一 IP、同一规范化邮箱分别 10 次/分钟 | 429 |
| 注册请求 | 同一 IP 10 次/小时 | 429 |
| 新生成任务，包括有意重试 | 每用户接受 10 次/分钟 | 429 |
| 每个用户活动任务 | 跨会话合计 2 个 QUEUED 或 RUNNING | 429 |
| 同一会话活动任务 | 1 个 QUEUED 或 RUNNING | 409 SESSION_BUSY |
| 服务并行执行 | 4 个任务 | 有容量则排队 |
| 等待队列 | 20 个 QUEUED 任务 | 满载时 503 |

频率计数使用单进程内存，服务重启后重置，这是 Demo 的明确简化；持久化的活动任务不能跟着清零。部署在反向代理后时只信任配置的代理来源，不直接信任任意客户端提交的 IP 转发头。

新生成请求先按 API 规则验证身份和查找幂等记录，重复请求返回原回执，不重复消耗生成配额。单进程内串行协调并发准入和容量预留，事务失败撤销预留；不能用无锁的“先数一下”突破上限。数据库唯一约束、会话占用检查仍不可省略。被拒绝的新请求不留下 USER 消息、尝试或幂等键。

## 2. Demo 的数据库逻辑设计

### 2.1 八张业务表

以下是逻辑结构，不是可直接运行的建表 SQL。沿用原文档中合适的业务概念，Demo 单独编写迁移，不机械叠加完整 Coding Lab 的所有表。

| 表 | 主要数据 | 约束和职责 |
|---|---|---|
| `users` | 用户 ID、规范化邮箱、密码哈希、显示名、账号状态、时间 | 邮箱唯一；业务归属根节点 |
| `auth_sessions` | 登录 ID、凭据哈希、用户 ID、到期时间、撤销时间 | 凭据哈希唯一；查询时验证到期和账号状态 |
| `chat_sessions` | 会话 ID、用户 ID、标题、`title_is_manual`、状态、`last_activity_at`、`active_attempt_id`、时间 | 直接属于用户；当前任务指针由受保护事务维护 |
| `messages` | 消息 ID、会话 ID、角色、正文、`client_message_key`、`in_reply_to_message_id`、创建时间 | 用户消息和成功的最终回复；正文不被重试覆盖 |
| `generation_attempts` | 尝试 ID、会话 ID、用户消息 ID、状态、`retry_key`、`deadline_at`、执行者 ID、开始/结束时间、错误、回复消息 ID | 每次尝试独立记录；最终状态不可回退 |
| `memory_profiles` | 用户 ID、`profile_version`、更新时间 | 每用户一条；协调记忆并发写入 |
| `agent_memory` | 记忆 ID、用户 ID、`memory_key`、分类、规范化事实、摘要、证据数、状态、最新有效来源顺序、时间 | 以用户和稳定主题定位记忆；不以摘要文字判重 |
| `memory_evidence` | 证据 ID、用户 ID、来源 USER 消息 ID、`memory_key`、规范化事实、处理结果、审计尝试 ID、时间 | 去重与记忆改动在同一事务提交；保留来源而非重复聊天副本 |

### 2.2 必须落到数据库的约束

- `messages(session_id, client_message_key)` 唯一，键只用于 USER 消息；ASSISTANT 的该字段为空。
- `messages(in_reply_to_message_id)` 对非空值唯一，保证一个 USER 消息最多对应一条成功最终回复；USER 的该字段为空。
- `generation_attempts(session_id, user_message_id, retry_key)` 唯一；首次发送的尝试不需要重试键，通过用户消息找到原始尝试，不能错误地把最新重试当作原始发送回执。
- `memory_profiles(user_id)` 唯一。
- `agent_memory(user_id, memory_key)` 唯一；主题和值的规范化由适配层统一处理。
- `memory_evidence(user_id, source_user_message_id, memory_key)` 唯一。
- 会话、消息、尝试、结果回复的关联必须验证一致；不能只因某个 ID 存在就允许跨会话引用。
- 索引覆盖用户会话排序、会话消息分页、每条问题的最新尝试、待领取任务、到期任务和用户记忆查询。数据库主键对外仍以字符串表示。

### 2.3 标题与活动时间

- 新会话使用默认标题；首条消息生成简单标题，规则沿用 API 文档。
- 用户手动命名后设置 `title_is_manual=true`，后端不再用消息覆盖标题。
- 创建会话时初始化 `last_activity_at`；接受新消息、接受重试、成功保存最终回复时更新。失败结算、浏览历史或改名不提升排序。

### 2.4 与完整数据库文档的区别

完整 [Coding Lab 数据库设计](2026-09-18-ai-coding-assistant-database-design-zh.md)保持不变。Demo 的 `chat_sessions` 和 `agent_memory` 直接关联 `user_id`，不要求 Enrollment、Lab 或题目，也不预置教学实体。

新增的登录记录、尝试记录、版本及证据存储用于落实 Demo 契约，不声称原数据库文档已经包含它们。未来接入课程时另行设计数据迁移，不能假定这些聊天原本就属于某个课程。

## 3. Deep Agents 上下文和记忆接入

### 3.1 三种状态分开保存

| 内容 | 保存和使用方式 |
|---|---|
| 完整聊天历史 | MySQL 持久化，页面分页读取 |
| 跨会话 Profile Memory | MySQL 持久化，按用户隔离 |
| 单次执行的工具过程、临时文件与状态 | 按 `attempt_id` 隔离，第一版不持久化中途 checkpoint |

所有 AI 对话必须经过 Deep Agents。每次执行从 MySQL 重建输入，不维护另一份长期 checkpoint 聊天历史后再重复追加全量消息。服务重启不能恢复到模型生成一半的位置，但已提交历史和记忆仍在。

### 3.2 上下文组装

1. 后端从可信登录与任务记录确定用户、会话和当前 USER 消息。
2. 查询当前会话最近最多 20 轮成功问答；一轮由一个问题和其成功的最终回复构成。
3. 读取当前用户记忆及同一快照中的版本，加入所需系统指令和工具定义。
4. 在模型总预算内为输出预留空间；超预算时从最早的完整问答轮开始移除。
5. 当前问题完整加入一次。重试不重复加入原 USER 消息，不带入失败的临时回答；旧失败问题不算成功问答轮。

20 轮只是输入模型的上限，不限制数据库保存数量。当前问题本身不能容纳时，在接受生成任务前返回 `422 CONTEXT_TOO_LARGE`，不偷偷截断，也不留下新消息或尝试。重试同样重新检查当前配置下的输入预算。

模型、分词方式、上下文容量和输出预留量需要在接入时配置并验证。用户不通过请求体指定模型或提交一份自造历史来绕过后端。

### 3.3 MySQL 记忆适配

- 将数据库中当前用户的有效摘要投影为虚拟 `/memories/profile.md`，通过 Deep Agents 的 `memory` 能力读取。
- 此路径不是宿主机上的真实文件，也不是第二份记忆存储。同一路径对不同用户返回各自的数据，不使用全局共享 Profile 缓存。
- 自行实现内部工具 `save_profile_facts`，提交具体主题及事实改动，而不是覆盖旧 Profile 全文。此名称是本项目自定义工具，不是 Deep Agents 自带函数，也不增加公开 API。
- 虚拟 Profile 对通用文件写入工具只读；所有记忆写入必须经过受控适配层。临时工作区不能成为读取宿主文件或其他用户记忆的入口。
- 用户 ID、来源消息 ID、尝试 ID 由可信后端上下文注入，不允许模型指定。候选事实必须有用户明确陈述依据；Profile 内容作为用户数据处理，不能提升为能够改变权限的系统规则。
- 工具返回实际提交结果；只有成功落库才可宣称“已记住”。成功后刷新本次执行的记忆视图和版本；记忆失败不使正常回答自动失败。
- Profile Memory GET 读取同一份 MySQL 权威数据，不临时调用模型生成页面内容。

框架能力依据：[Deep Agents Memory](https://docs.langchain.com/oss/python/deepagents/memory)介绍记忆路径及读取方式，[Backends](https://docs.langchain.com/oss/python/deepagents/backends)介绍存储适配。上面的 MySQL 投影和受控写工具是本项目设计，不是声称框架自动提供了用户认证、表结构和冲突解决。

### 3.4 版本、合并与证据

严格遵守 API 第 9.2 节：读取时取得 `base_version`，提取改动在事务外进行，写入按“会话 → 尝试 → 用户 Profile”锁顺序执行；取得全部锁后复查当前任务有效、RUNNING 且未过期。

先查来源去重，再对新改动比较版本。同版本时将事实、证据和版本递增原子提交；冲突则重新读取内容、重新合并，最多 3 次提交尝试且受任务截止时间限制。不能只换版本号后强行保存旧全文。

不同主题保留；同含义复用；单值偏好冲突按来源消息的 `created_at + message_id` 判断新旧，不按生成完成顺序。已处理的同一来源同一主题不再次计数，重试改变 `attempt_id` 也不构成新证据。`evidence_count` 只统计支持当前有效事实的不同消息。

超时前已提交的记忆不因回答失败回滚；失效后提交的改动被拒绝。事务提交结果不明时先查证据和版本，不能盲目补写。

## 4. 生成任务执行与恢复

### 4.1 单进程部署边界

一个 FastAPI 服务进程运行服务内任务执行器，MySQL 的 `generation_attempts` 保存队列和结果。第一版不引入 Redis、Celery 或多实例；4 个执行槽位是同一进程内的并行任务，不是 4 个 Uvicorn worker。

执行器由应用生命周期管理，持有任务引用并处理异常，与某个 HTTP 请求的生命周期分离。SSE 连接只是订阅者：浏览器关闭不取消已接受的任务。不得仅依赖随响应结束而终止的请求协程来生成答案。

### 4.2 接受、领取和完成

1. 验证登录、归属、参数、幂等、上下文预算与容量。
2. 在短事务中创建 USER 消息（重试则复用）、QUEUED 尝试、截止时间和当前任务指针，必要时初始化标题；成功提交后才表示接受。
3. 执行器按 API 第 6.5 节锁定会话和尝试；仅当前、未过期的 QUEUED 可领取为 RUNNING，记录执行者。重复领取不得再次调用模型。
4. 事务外加载上下文和执行 Deep Agents；通过按尝试隔离的事件通道转发用户可见回答，不发送内部工具内容或模型推理。
5. 完成后在同一短事务中复查许可、保存最终回复、标记 SUCCEEDED、清除自己的占用；提交成功后发送完成事件。
6. 错误、超时也通过同一套锁与状态检查结算；不能由旧任务清理代码无条件清空当前任务指针。

SSE 订阅登记与执行启动必须协调，避免任务已发出片段而首次订阅尚未建立。通道按尝试隔离并限制缓冲；断线或慢客户端不能无限占用内存或拖住模型。通道不做持久化片段重放，数据库结果仍是恢复依据。

### 4.3 截止时间和迟到结果

默认从接受请求起计算 180 秒，覆盖排队、Agent 执行和最终保存前等待。每秒扫描一次到期任务；扫描不是唯一保护，取得数据库锁后还必须检查数据库时间。网络重发不延长预算，有意重试创建新尝试才有新的预算。

成功和超时只允许一个最终状态提交。超时事务标记 FAILED 并释放自己的占用后尽力取消执行；即使取消失败，迟到回复和记忆也无法通过写入检查。前端按 `attempt_id` 和终止状态忽略旧片段。

180 秒是应用的任务预算，不保证数据库故障或锁等待期间在精确的第 180 秒就完成失败落库。提交结果未知时先核对，不能伪报成功或盲目判失败。

### 4.4 断线和重启

- 浏览器断线：继续执行；回来后读取历史，仍生成时有界轮询，结束后展示最终消息。不补播断线期间的 token，不因断线自动发起重试。
- 服务重启：部署先保证旧进程完全退出，再启动新进程；完成数据库恢复后才接收新生成请求。
- 旧 RUNNING：受保护地标记 FAILED，错误 `GENERATION_INTERRUPTED`；若已到期使用 `GENERATION_TIMEOUT`。不把同一个尝试重新分配给新执行者，由用户决定重试。
- 旧 QUEUED：已过期则结算超时，未过期可领取；根据持久化记录恢复用户占用和队列。
- 已完成数据：不改变已有最终状态、回复或记忆。若上次提交确认丢失，以数据库实际结果为准。

未来多进程、多实例或滚动更新需要另外设计执行者存活判定、共享容量、共享限流和事件分发；不能把这里的“启动即恢复旧进程任务”直接用于其他仍在运行的进程。

## 5. 基础功能验收设计

| 层次 | 验证内容 |
|---|---|
| 规则测试 | 参数、最终状态不可回退、重试资格、上下文预算、记忆合并和去重 |
| 真实 MySQL 接口测试 | 登录持久化、权限、事务回滚、唯一约束、分页、并发领取与配额准入 |
| 浏览器端到端测试 | 注册登录、侧栏、发消息、流式回复、刷新恢复、失败重试、跨会话使用记忆 |
| 真实模型接入验证 | Deep Agents 实际执行、所选模型的工具调用、记忆加载和可见回答流式适配 |

用可控制返回时机的模拟模型制造失败、断线、重复回调、超时和迟到结果，不依赖真实模型碰巧出错。数据库锁和事务测试使用真实 MySQL，不能只用进程内模拟或 SQLite 证明正确。

至少通过：

1. 用户 A 无法通过 UI 或直接请求访问 B 的会话、消息、尝试与记忆。
2. 同时提交相同消息键只保存一次 USER、启动一次生成；不同内容复用键被拒绝。
3. 登录 7 天到期后失效；退出只撤销当前凭据；重启保留未到期登录。
4. 流式片段不被拆成多条数据库消息；失败的部分回答不作为最终回复保存。
5. 断线不取消生成；刷新后从数据库恢复结果，网络重发不自动生成第二遍。
6. 超时 A 后重试 B，A 的迟到回复、片段、记忆写入和清理不能改变 B。
7. 队列满、用户超限、会话忙和上下文超限不留下被拒绝的新消息、尝试或幂等键。
8. 排队超时和服务退出后的遗留任务最终能够结算；已提交的成功结果不被恢复逻辑改成失败。
9. 分页边界包含时间与 ID，同一时间的多条消息不遗漏；侧栏动态排序按 API 约定去重和刷新。
10. 最近 20 轮及模型预算处理不重复当前问题、不把失败片段加入输入，也不删除页面历史。

以上是待执行验收清单，不代表测试已通过。

## 6. 每条问题与会话摘要的一致性

不另存一份容易过期的消息状态缓存。历史接口批量查询本页每条 USER 消息最新创建的尝试，计算 `items[].generation`；会话级 `latest_generation` 查询整个会话的最新尝试，不能局限于当前页。

消息、最新尝试和重试资格从同一读取快照组装，避免同一尝试在响应中同时显示 RUNNING 与 SUCCEEDED。`can_retry` 使用整个会话最新 USER 消息及会话状态判定；实际重试事务仍重新检查。

必须验证：

- 旧问题失败 → 新问题成功 → 刷新：旧问题保留错误摘要，且 `can_retry=false`。
- 最新问题进入重试：消息级与会话级摘要都指向新尝试，不表示旧 FAILED 尝试被复活。
- 查询旧历史页：不能把本页最后一个问题误认为全会话最新问题。
- 重试过程中、成功提交前后并发查询：单个响应内部状态一致，不产生部分已成功的视图。

## 7. 记忆并发验收设计

通过测试屏障控制两个任务读取旧版本、等待锁和提交的先后，真正构造并发而非只串行调用两次接口。

| 情形 | 预期结果 |
|---|---|
| A 保存中文偏好，B 基于同一旧版本保存学习 Python | 冲突方重读合并，两条都保留 |
| 新英文偏好先提交，旧中文偏好后到 | 旧来源不能覆盖较新来源 |
| 同一 USER 消息重试或工具重复调用 | 同一主题一份来源证据，纯重复不升版本 |
| 两条不同消息表达同一事实 | 复用记忆条目，独立证据可以增加 |
| 写入事务回滚或版本冲突 | 记忆、版本和证据都不能部分提交 |
| 取得 Profile 锁时尝试已经超时或失效 | 拒绝迟到记忆写入 |
| 记忆提交成功后回答超时 | 已提交记忆保留，后续重试不重复计数 |
| 提交确认丢失 | 查询已持久化证据后恢复，不盲目再次累加 |
| 持续冲突达到 3 次提交尝试上限 | 保留已有记忆，回答可继续，不谎称保存成功 |
| A、B 用户访问相同虚拟 Profile 路径 | 只返回各自记忆，不通过缓存或工具跨用户读取 |
