## 1. 总体结构与运行边界

React + TypeScript 前端，FastAPI 后端，MySQL 保存数据。所有 AI 聊天经过 Deep Agents。只运行一个后端进程和一个服务实例，模型执行使用可取消的异步调用；不配置多个 Uvicorn worker。

会话并发保护依靠该进程中的运行登记和短锁。它适合当前演示部署，不提供多进程或分布式协调。数据库唯一约束和事务仍保留。

- 同站点页面 /，业务接口 /api/v1；本地用开发代理，部署使用 HTTPS。
- 登录用 chat_session Cookie 与 MySQL auth_sessions，固定 7 天、不自动续期；退出只影响当前凭据。
- Cookie 设置 HttpOnly、SameSite=Lax、Path=/；HTTPS 使用 Secure。写操作验证受信任 Origin。
- 密码使用专用密码哈希；数据库只存登录凭据哈希。模型密钥在后端环境配置，不能进入 Git、浏览器或日志。
- 简单限流沿用 API 第 2.3 节，计数保存在进程内存，重启重置；不建设等待队列和持久化容量管理。
- 阶段 0 可提供 GET /health 检查连通性，不计入 11 个业务接口。

## 2. 五张核心表

### 2.1 逻辑结构

下表用于指导 ORM 和 Migration，还不是建表 SQL。字段命名在后续代码中统一，API 对外 ID 一律表示为字符串。

| 表 | 主要字段 | 职责 |
|---|---|---|
| users | user_id、email、password_hash、display_name、账号状态、created_at | 账号与用户身份 |
| auth_sessions | 登录 ID、user_id、token_hash、expires_at、revoked_at、created_at | 服务端登录状态 |
| chat_sessions | session_id、user_id、title、title_is_manual、last_activity_at、created_at、updated_at | 会话归属、默认标题和侧栏排序 |
| messages | message_id、session_id、role、content、client_message_key、in_reply_to_message_id、attempt_id、retry_of_attempt_id、generation_status、generation_error_code、generation_error_message、created_at、updated_at | 用户问题、成功的最终回复、每条问题最近一次生成的状态 |
| agent_memory | memory_id、user_id、memory_key、memory_type、summary、created_at、updated_at | 按用户和主题保存个人记忆 |

不创建 generation_attempts、memory_profiles、memory_evidence。不实现归档字段和持久化的当前任务指针、任务截止时间。

messages 的生成元数据仅用于 USER，ASSISTANT 相应字段为空。每次重试只替换 USER 的最新运行编号和状态，不保留完整尝试历史；问题正文及创建时间保持不变。ASSISTANT 使用 in_reply_to_message_id 关联问题。

### 2.2 必需约束和索引

- users.email 规范化后唯一。
- auth_sessions.token_hash 唯一，支持按用户和到期时间查询。
- messages(session_id, client_message_key) 唯一；ASSISTANT 的消息键为空。
- messages.in_reply_to_message_id 的非空值唯一；一个问题最多有一条成功最终回复。
- agent_memory(user_id, memory_key) 唯一。
- 建立用户会话排序、会话消息排序和用户记忆查询所需索引。
- 校验回复、原问题和会话关系一致，不能仅依赖一个 ID 存在就允许关联。
- 模型调用在事务外进行；成功回复插入与 USER 成功状态在同一短事务中提交。

### 2.3 标题、排序与读取

首条问题生成前 30 字符的简单标题；手动改名后 title_is_manual=true，不能再自动覆盖。创建时初始化活动时间，接受新消息、接受重试、保存成功回复时更新；改名、阅读和失败结算不提升排序。

左侧栏一次查询本人的全部会话列表，包含标题和会话 ID 等信息，不同时加载所有会话的消息。点击某个会话后，再一次读取这个会话的全部历史消息，按创建时间、ID 从旧到新显示。这里说的“全部”用于页面展示，不表示全部交给模型。当前演示数据较少，不做分页，也不能静默截断却假装返回全部；数据量扩大时再补分页。

### 2.4 与完整教学系统的区别

[完整数据库文档](2026-09-18-ai-coding-assistant-database-design-zh.md)继续描述 Coding Lab。Demo 的会话和记忆直接关联 user_id，不预置课程、Lab、题目和 Enrollment。

本版消息表增加最新生成元数据来支持失败重试。记忆只覆盖明确陈述的偏好、目标和编程背景，使用 LEARNING_PREFERENCE、LEARNING_GOAL、PROGRAMMING_BACKGROUND；不沿用完整教学系统的所有分类或证据字段。今后引入课程、审计历史和证据模型时另做迁移。

## 3. Deep Agents 与上下文

### 3.1 页面历史与模型上下文分别加载

**页面让用户查看历史，模型上下文帮助 AI 回答当前问题，两者读取范围不同。**

| 场景 | 加载范围 | 用途 |
|---|---|---|
| 打开左侧会话栏 | 当前用户的全部会话列表，不包含各会话的全部消息正文 | 让用户选择对话 |
| 点击某个会话 | 这个会话的全部历史消息 | 在页面上查看和回顾，不做分页 |
| 发送新问题或重试失败问题 | 当前会话最近最多 20 轮成功问答、当前问题和当前用户的 Profile Memory | 交给 Deep Agents，作为模型回答时的上下文 |

后端从登录和数据库确定用户、会话及问题，再组装模型输入。一轮成功问答指一个用户问题及其成功保存的 AI 回答；当前问题另外完整加入一次，不算在之前的 20 轮里。其他会话的聊天原文不会一起加入，跨会话使用的是该用户已保存的 Profile Memory。

例如，一个会话已经有 100 轮成功问答：页面能展示全部 100 轮；回答新问题时，模型最多收到其中最近 20 轮。更早的消息仍保存在数据库中，也仍可在页面查看，并没有被删除。20 轮是本项目选择的可配置上限，不是 Deep Agents 强制要求。

模型一次能处理的内容有限，按 token（模型处理文字的计量单位）计算。除历史问答外，还需为系统提示、工具定义、记忆、当前问题和输出预留空间；若总量超限，就从选中的最早一轮完整问答开始移除，因此实际可能少于 20 轮。当前问题本身放不下时，接受请求前返回 422 CONTEXT_TOO_LARGE，不能偷偷截断。

重试时原问题只加入一次；失败问题的半截回复不进入上下文。已保存消息是历史事实，不再从持久化 checkpoint 追加另一份重复历史。临时 Agent 状态以本次 attempt_id 隔离，不保存可恢复的中途 checkpoint。

### 3.2 记忆读取

将当前用户 agent_memory 条目投影为虚拟 /memories/profile.md，供配置后的 Deep Agents memory 能力读取。此路径不是实际磁盘文件，不额外维护一份 Profile；相同路径对不同用户映射到各自数据。

页面 GET /api/v1/me/memory 直接读取同一份 MySQL 数据。记忆内容是用户数据，不允许它改变身份、访问权限或后端工具范围。

### 3.3 记忆写入

给 Agent 配置项目自定义工具 save_profile_facts，提交具体主题和值。此函数需要我们实现，不是框架自动提供的 MySQL 接口。

- user_id、当前问题和运行编号由后端注入，模型不能指定其他用户。
- 只提取用户明确表达的学习目标、编程背景和回答偏好；含义不明则不更新。
- 使用稳定主题，例如 preference.language、preference.explanation_style、learning.goal、learning.current_topic、programming.level。初版限制在这些主题内，每条摘要最多 500 字符。
- 按 user_id + memory_key 更新或插入，只处理此次涉及的主题；不拿旧 Profile 全文覆盖数据库。
- 不同主题的更新互不覆盖。同主题同时修改采用实际数据库提交顺序后写生效，本版不承诺按原陈述时间自动裁决冲突。
- 用唯一约束避免重复条目；不计算 evidence_count，不维护来源证据台账或用户级 profile_version。
- 工具实际提交成功后才能返回已保存；失败时保留原记忆，并允许 Agent 继续正常回答。
- 记忆通用文件接口只读，所有写入走上述工具；临时工作区不能访问宿主机文件或其他用户数据。
- 工具写入前确认本次执行仍有效；取消后不启动新的写操作。已提交或已进入提交阶段的短事务先确定结果，完成清理再允许新的生成。

重试可重新更新相同主题，不会累加出重复条目。回答失败前已经成功提交的记忆继续保留，不承诺与整轮聊天一起回滚。复杂并发合并与证据计数是后续迭代。

框架接入参考：[Deep Agents Memory](https://docs.langchain.com/oss/python/deepagents/memory)、[Backends](https://docs.langchain.com/oss/python/deepagents/backends)。具体库版本与适配方法在阶段 0 和模型接入时核验。

## 4. 最小生成控制与失败重试

### 4.1 同一会话只能有一个生成

单进程维护 session_id 到运行上下文的登记，记录本次 attempt_id、取消状态和任务引用。登记的创建、替换和清除必须原子化；不能仅由前端禁用按钮。

使用短临界区协调准入、最终保存及状态读取，不在其中等待模型。忙碌状态跨越整个执行与清理过程。新发送和重试共用该控制；其他会话可以独立生成。

先认证、查重，再检查新请求是否忙碌。消息接受事务失败时撤销自己的占用，不能遗留半条消息或幂等键。

### 4.2 共用生成过程

接口层先完成发送或重试的登记，然后调用同一个聊天服务：

1. 加载问题、历史和记忆，发出 message_start。
2. 运行 Deep Agents 的异步流，筛选用户可见文字，发送 message_delta，同时在后端拼接最终正文。
3. 正常结束后核对消息上的当前 attempt_id 与 RUNNING 状态，原子保存最终回复和 SUCCEEDED。
4. 提交确认后发送 message_done；已确认失败时保存 FAILED 与简短错误，发送 message_error。
5. 结束与清理只释放仍属于本次编号的会话占用。迟到回调和片段不得改写另一轮执行。

片段不逐条写入消息表。通用工具事件、系统提示、模型推理不能直接转发给页面。模型完成与数据库保存成功是两件事，不能在保存前告诉前端“已完成”。

### 4.3 重试需要哪些最小数据

重试只针对整个会话最新 USER 且当前生成已确认失败的情况，成功回答不能重新生成。

前端提交 failed_attempt_id，服务在短临界区中检查它是否等于当前失败编号。接受后生成新的 attempt_id，把旧编号记为 retry_of_attempt_id，状态置 RUNNING，并清空旧错误；原问题不再插入。

如果 retry_of_attempt_id 已经等于请求编号，说明同一次失败已经被重试过，返回当前结果回执，不重复启动。更早的旧请求返回状态过时冲突。若这次重试也失败，用户拿到新的失败编号后可以再重试。

因此不需要新增尝试表或保存所有 retry_key。只有最近一次状态和直接前驱编号；本版不提供任意旧重试的历史回执。详细请求和响应见 API 第 6.4、8 节。

### 4.4 请求超时与取消

采用默认 120 秒的请求级 Agent 超时，可配置；同时配置模型网络调用超时，避免底层请求无限等待。其范围包括本次 Agent 工具循环，不为每次工具后模型调用重置整轮预算。

不保存绝对 deadline、不每秒扫描、不持久化排队。超时触发取消并标记本次运行无效，不接受它之后的新写入。使用可取消异步模型与工具调用，避免另起不受管理的线程或后台回调直接写数据库。

取消不等于远端模型一定停止。回复保存仍检查“当前编号一致且 RUNNING”；清理必须完成或确认残留执行无法再写入，才释放会话。不为了按时清除 UI 忙碌状态而放任旧本地任务继续写库。简单超时不保证数据库故障期间能在精确第 120 秒完成结算。

### 4.5 断线与重启边界

第一版请求断开后不承诺后台继续生成。检测到断线时取消，能记录则保存 FAILED / GENERATION_INTERRUPTED。前端断线时先查询历史，结果已保存则展示；仍在清理就保持忙碌，不盲目点击重试。

部署只允许旧进程完全退出后再启动新进程。启动接收请求前核对残留 RUNNING：若已经有成功回复则确认成功，否则标记中断失败。完成历史和记忆原样保留；不恢复执行、不领取旧任务、不自动重调模型。这是一次简单状态清理，不是完整任务恢复系统。

数据库提交结果不明时先核对，不同时启动重试或写相反最终状态。暂时无法持久化错误时，连接恢复后核对并只清理已确认没有存活执行者的残留状态，不能误伤仍在运行的请求。状态读取与运行登记协调，避免已无执行者却永久显示 RUNNING。

## 5. API 与前端约定

仍为 11 个业务接口：账号 4 个、会话 3 个（新建/列表/重命名）、消息 3 个（历史/发送/重试）、记忆 1 个。

PATCH 仅接受 title；无归档入口。列表与历史无 cursor 分页。历史返回每条问题的 generation 和会话 is_generating，不返回完整尝试历史。

发送和重试都用 POST + fetch 接收 SSE，按空行解析事件；不能假定每个网络块是一个完整 JSON。失败重试时替换原问题下面的临时失败气泡，按新 attempt_id 隔离，保持原问题不重复显示。

前端显示正在生成、完成、失败和连接结果待确认。只有 can_retry=true 才显示可点击重试。Markdown 净化或禁用原始 HTML。先完成可用界面，视觉细节后调。

## 6. 第一版必须通过的验收

这些是待执行检查，不代表已通过。

| 场景 | 预期 |
|---|---|
| 注册、登录、退出、重新登录 | Cookie 行为正确，凭据与密码不泄露 |
| A 直接访问 B 的会话、消息和记忆 | 后端拒绝，不只依赖前端隐藏入口 |
| 发送问题 | 每次经过 Deep Agents，SSE 可逐步显示，最终只存一条回复 |
| 刷新或重启 | 已提交历史、记忆和有效登录保留 |
| 同一会话同时发送或发送时点重试 | 一个运行，其他新请求被拒绝且不留多余消息 |
| 相同 client_message_key 重发 | 不重复保存问题或调用模型 |
| 模型报错、超时 | 明确失败，不把半截回复存成最终回答 |
| 最后一个失败问题点击重试 | 原问题不重复，SSE 新回答成功保存 |
| 重试请求重复或较旧请求延迟到达 | 不多生成；返回当前回执或状态过时冲突 |
| 成功问题或已有后续问题的旧失败问题点重试 | 拒绝 |
| 原任务取消后迟到内容 | 不覆盖新尝试，不清除新占用 |
| 断线发生在成功提交前后 | 查询历史确认结果，不把已成功回答误当失败重试 |
| Agent 保存中文偏好，新建会话提问 | Memory 页面可见且新会话实际使用 |
| 同主题反复保存、不同主题分别保存 | 同主题一条记录，不同主题都保留 |
| 旧问题失败、新问题成功、刷新 | 旧问题保留失败提示但不可重试 |

失败、超时和重复请求使用可控制的模拟模型验证；数据库约束用真实 MySQL 验证。再用实际模型检查 Deep Agents 工具调用、记忆与流式输出，最后走一次浏览器演示流程。暂不要求旧版完整任务队列和记忆版本冲突测试矩阵。

开发排期仍按五天安排，与版本名称分开记录：第 1 天环境和数据设计，第 2 天迁移及账号会话业务，第 3 天聊天、Agent 与 Memory，第 4 天业务 API、SSE 与可用页面，第 5 天重试等边界联调、演示和修复。业务重试逻辑仍在第 5 阶段实现，第 5 天检查的是整体验收。页面壳可以提前准备，不能把模型、Memory 或 SSE 的首次验证都留到最后一天。

## 8. 暂缓与后续选择

暂缓：归档、cursor 分页、持久化任务队列、完整生成尝试历史、180 秒截止时间扫描、多进程协调、执行 checkpoint 恢复、记忆版本合并、来源证据计数、成功回答重新生成。课程、Lab、Enrollment、RAG、上传和评分也不在范围内。

模型服务商与型号、依赖兼容版本、模型输入输出预算和实际部署地址在环境阶段及接入时落实。本次只是对齐设计，不能当成已经安装依赖、连接模型、建好表或通过测试。
