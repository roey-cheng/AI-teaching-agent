### 页面画面对照与已发现问题

本地提供的 artifact-tool 渲染脚本因缺少 runtime node_modules 无法运行。本次使用已安装的 Keynote 导出临时 PDF，再渲染页面进行核对；没有在 PowerPoint 中验证，因此不能宣称与 PowerPoint 渲染完全一致。PPTX 导入 Keynote 可能发生字体或布局差异，原始文件和原生结构仍需保留。

已视觉核对 Composite 第 11、12、14 页，Mouse 第 4、5、7、8 页：

1. **图片文字缺失。** Composite 第 12 页的类名、方法、UML 关系等在大图里。原生 Docling 文本基本只有标题与页码；仅把 Markdown 入库会遗漏核心内容。18 个图片对象不是 18 张独立教学示意图，组合对象和重复素材需要处理。
2. **代码没有形成代码块。** 两份 PPTX 的 Docling 输出均没有 `code` 标签。Mouse 第 5～7 页代码被分成多个普通段落；需根据原生文本框恢复代码边界、换行和缩进，不能按段落分别切块。
3. **不能依赖单一线性阅读顺序。** Composite 第 14 页比较左右两套代码与类图，导出的文字顺序先右后左；切块时必须保存文本框位置、组合关系和左右分组。
4. **源文件有不可见/装饰性残留文字。** Mouse 第 7 页两个矩形内含字符 `v`，原生提取能读到，但在本次渲染中不构成可见正文。第 8 页有白色的 `Model / Subject / Observable` 与 `View / Observer / Listener` 文本，导出文字包含它们，但页面对照看不到。不能把“提取到了”当成“学生看得见”。
5. **边界警告不等于文字缺失。** Mouse 第 7 页右侧代码框超过页面宽度，Docling 发出 bbox 越界警告；原生代码文字仍被提取，渲染中的代码也可读。需保留原始坐标并另外计算裁剪坐标，不能因为警告自动删除内容。
6. 本样本没有非空备注、隐藏页或动画时序节点；这些功能的处理规则仍需专门测试，不能由本次结果推断支持完整。

因此当前结论是：**两份文件可解析，但裸 Docling Markdown 不满足正式 RAG 的完整性要求。**

## 2. 导入器的边界与产物

第一版是管理员在本地运行的离线命令，不是上传即执行的聊天工具；先完成这批资料的准备与人工审核，再接入 MySQL/Milvus 发布。解析与模型调用不放在 FastAPI 请求内，也不放在 Railway 的每次启动或 pre-deploy 中。

固定工具与模型分工：

- Docling：解析文档并统一正文、表格、图片与来源信息；PPTX 用 `python-pptx` 补充原生文本框、代码换行、位置与组合层级。
- RapidOCR：仅用于没有可靠文字层、以文字为主的扫描页/扫描区域；已有可靠原生文字和已交给 Flash 的完整教学图不再默认重复 OCR。
- `deepseek-flash`：直接读取选定教学图中的文字并解释关系，不要求先经过 OCR，不作为原始代码的权威转写来源。
- `pypdfium2`：需要给 OCR/Flash 提供 PDF 页面或区域画面时，在后台生成图片。
- LibreOffice headless：只为必须看整页/组合画面的 PPTX 生成临时 PDF，随后用 `pypdfium2` 生成图片；不是所有 PPTX 的必经步骤。
- SiliconFlow `Qwen/Qwen3-Embedding-0.6B`，1024 维：审核通过的文本块以及检索问题向量化。

### 处理路线：按内容分流，不串行叠加全部工具

| 内容 | 主处理工具 | OCR | 额外生成页面图片给 Flash |
|---|---|---|---|
| PPTX 原生文字、代码、表格 | Docling + python-pptx，直接提取 | 不需要 | 通常不需要 |
| PDF 中有可靠文字层的正文、代码、表格 | Docling，保留原文与结构 | 默认关闭，缺失区域再处理 | 通常不需要 |
| PPTX/PDF 中独立且完整的 UML/流程图图片 | 提取原图，直接发 Flash；附带页标题与相关原生文字 | 默认不做 | 不需要，原图已是可见画面 |
| PPTX 中由文本框、线条、多个图片组成的教学图，或必须对照左右布局的页面 | LibreOffice 后台转 PDF → pypdfium2 出图 → Flash | 默认不做 | 需要，否则可能丢失连接或对应关系 |
| PDF 中由矢量线条与文字共同组成的教学图 | pypdfium2 生成区域/页面图片 → Flash | 默认不做 | 需要，无须 LibreOffice |
| 没有可靠文字层、以文字为主的扫描页 | 直接使用完整扫描图，或 pypdfium2 出图 → RapidOCR | 使用 | 不默认交给 Flash；混合页仅另选复杂图区域 |
| 看不清、可见性存疑、图被拆散而无法确认完整的内容 | 标记待审核/待渲染 | 不盲目重跑 | 按问题选择，不悄悄省略 |

这里的“渲染”只表示把文档元素按位置生成一张图片，不是识字、生成新图，也不是控制用户电脑打开软件截图。例如原生提取读到 A、B、C 三个文本框，并不等于已经理解 A→B 还是 A→C；完整画面可以让 Flash 看见线与文本框的对应。若这张图本来就是一张完整 PNG，直接提取它即可，没有必要再渲染整页。

表中的“额外生成页面图片”是指供 Flash 看图的步骤。Docling 的 PDF 版面分析内部也可能栅格化页面；这不等于额外跑 OCR 或发给大模型，更不涉及桌面控制。

第一版先输出内容类型与处理路线清单。根据原生文字、图片和图形对象识别候选，不靠“文字少”一个条件判断；存疑页面进入审核。只有确认图是完整独立图片时才直接使用原图，否则保留其组合区域/页面。相邻文字与图片通过页号、位置和组 ID 关联，避免把互不相关的内容配对。

后台渲染不模拟鼠标键盘，不启动 Keynote；使用独立临时目录、转换进程超时和固定字体环境，原文件只读。渲染器缺失或转换失败时标记 `needs_render`，继续其他文件，但该文档不得作为完整版本发布。先拿本批两份 PPTX 验证 LibreOffice 的页数、字体、代码框和箭头再启用，不能把之前 Keynote 的结果视为 LibreOffice 已通过。

已新增独立的 `tools/course_import/` 工具环境和入口，拥有自己的依赖锁文件；不把 Docling、OCR、渲染依赖装进线上聊天镜像。当前离线导入器不读取 API 密钥；未来付费阶段的密钥仅从服务端环境读取，日志不得打印密钥、完整请求体或学生资料。

完整生命周期的早期命令草案（并非当前可执行接口；当前命令以 README 为准，enrich/embed/publish 尚未实现；review 已实现，但使用 `--source` 与 `--output`，而非下面的 `--run` 草案）：

## 3. 批处理步骤

### A. 盘点与本地解析，不调用付费 API

1. 只接受 `.pdf`、`.pptx`；记录哈希、大小、页数、相对路径。明确拒绝宏文件，不执行嵌入对象、课件代码或文档中的命令，不自动抓取外部链接和远程图片。
2. 每个文件独立处理；默认一个解析任务，避免并发解析造成资源争用。单文件失败记录原因后继续其余文件，可从失败阶段恢复。并发数作为部署配置，不在项目文档中记录个人设备信息。
3. PDF 采用原生文字优先的 Docling 流程；本地盘点先识别扫描区域，普通文字页关闭自动 OCR。仅对没有可靠文字层且以文字为主的扫描区域安排 RapidOCR；复杂教学图走 Flash 分支。保留表格行列、页面位置和原图，原生代码不让视觉模型重写。
4. PPTX 同时保留 Docling 文档结构和原生 shape 信息：稳定的 shape ID、组合层级、文本框、字体/颜色线索、页面位置、图片、隐藏状态。按文本框保留代码，不依赖 Docling 是否打上 `code` 标签。
5. PPTX 原生提取不依赖任何 Office 应用。只有路线清单标记需要组合画面的页面，才安排 LibreOffice headless 转换，并只把所需页面/区域送入 Flash。转换工具可能生成整份临时 PDF，但不意味着每页都要 OCR 或付费解释。禁止回退到 Keynote、AppleScript 或桌面 UI 控制；不得保存覆盖原 PPTX。渲染失败进入 `needs_render`，不能仅凭文字提取成功发布。迁到 Linux 后需重新验收渲染器和字体环境。
6. 隐藏页、备注和可见性存疑的文字单独保存，默认不进入学生可检索正文。白字、越界、遮挡、孤立字符等只是审核信号，不能简单“所有白字删除”或“所有越界删除”。

### B. 识别需要图片补充的区域

1. 列出图片、原生组合图形、文字稀少但图形丰富的页面。根据重复图片哈希与跨页重复位置识别校徽、页眉等候选装饰，不按“有图片就调用 Flash”。
2. OCR 只执行路线清单中明确选择的扫描文字任务，保留文字、置信度和位置；低置信度与明显符号问题进入审核。高置信度也可能识别错括号，因此不得据此自动通过代码转写。不为已经交给 Flash 的每张教学图再额外跑 OCR，也不把全部 OCR 页面重复送给 Flash。
3. 独立且完整的图片直接使用原图；由图像、箭头和文本框共同构成的教学图才需要完整图组/页面画面，不把连接关系裁掉。图片密集不自动等于复杂图，候选装饰先过滤。
4. 首次先生成候选清单，再对选定教学图调用 Flash。默认并发 1，每次 enrich 最多 20 个请求；所有请求尝试均计数，达到上限就暂停，不默默全量调用。失败内容保持待处理，不以空描述冒充成功。
5. 输出必须分为“图上可见事实”“模型解释”“不确定之处”，并绑定页码、图片/区域 ID、模型与提示版本。禁止补写原文代码，不把图上提出的问题擅自改成已有答案。
6. 缓存键包含图像/渲染内容哈希、关联上下文、模型名、提示版本和参数。仅对变化的内容重跑。记录服务返回的 token 用量；费用只有在取得有效价格或账单时才能报告，不能臆估已扣款金额。

### C. 切块、审核与向量化

1. 第一版按页和教学内容块组织；附带文档标题与当前页标题。普通说明按段落聚合，初始目标约 600 tokens、上限 1000 tokens，使用固定版本的本地 tokenizer 计量并记录；这只是切块尺度，不冒充 API 的账单 token。
2. 代码、表格、UML 及其说明作为有类型的内容块。过大的代码按类/方法或完整行边界分片，表格分片重复列头；保留共同的父块 ID，支持读取完整上下文。绝不在任意字符位置裁断代码。
3. 每个块至少记录：库标签、文档 ID/版本、页或幻灯片号、元素 ID/区域、内容来源类型（原生/OCR/视觉说明）、文本、父块 ID、审核状态。对同页原生文本、OCR、视觉重复转写去重，但不能把相似的两种代码方案合并。
4. 自动检测孤立页码、缺失来源、异常空页、模型输出截断和不可见文本警告；疑似问题进入审核。原始结果保留，规范化索引文本单独生成。
5. 第一版逐项审核教学图的视觉说明、代码问题、图文对应问题和存疑可见性。未解决的实质缺失使文档保持待审核，不能只因为部分块成功就标记整份文档完整。
6. 审核通过后才调用 Embedding；固定 1024 维，验证条数、维度和有限数值。查询使用完全相同的模型与维度。更换模型/切块策略建立新索引版本，不把不兼容向量混在旧索引里。

### D. 发布与可恢复性

- 原文和元数据以 MySQL 为准，Milvus 保存可重建的向量索引，文件/图片单独存储。此阶段需要独立的建表、索引和部署实现，本次不执行。
- 文档 ID 不直接等于文件名；文件内容哈希标记修订版本。相同库内相同内容与配置重跑应复用结果，不能重复收费、重复插入。
- 新修订先写入暂存状态，完成 MySQL 数据、Milvus 向量数量和来源映射校验后，才切换“当前发布修订”。MySQL 和 Milvus 无跨库事务，失败时保留旧修订可用并允许重试。
- 检索必须过滤已发布且允许访问的修订，不能让暂存失败数据混入回答。回滚切回旧修订；移除文件不自动删除已发布内容，删除/撤回要显式操作。

## 4. 验收与实施顺序

先实现 `inventory + parse + review report`，以这两份 PPTX 与已经测试的 Template Method PDF 为样本；通过后本地解析其余 24 个文件。再补图像 enrichment、切块、Embedding，最后才做数据库发布和 Agent 检索接入。

必须通过的测试：

- 27 文件、652 页可逐项追踪；问题文件不阻塞整批，重跑跳过未变化的成功步骤。
- Composite 第 12 页的图中关键内容能被检索；第 14 页左右代码不会相互混淆。
- Mouse 第 5～7 页代码保持文本框内顺序和括号；第 7 页 `v` 与第 8 页不可见文字不混入已审核正文。
